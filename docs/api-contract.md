# API contract

Base URL: `http://127.0.0.1:8000`. JSON requests/responses; ISO-8601 UTC dates. Amounts in this demonstration are integer **whole INR**, not paise. The typed implementation agreement is [shared/schemas/api-contract.md](../shared/schemas/api-contract.md). FastAPI generates authoritative interactive docs at `/docs` and JSON at `/openapi.json`; [the checked-in snapshot](../shared/schemas/openapi.json) is generated by `scripts/smoke.py` from the actual running app.

All endpoints are local-demo endpoints without authentication. The original demo routes accept an optional `X-Demo-Role: household|provider`; workspace-write and chat routes require the matching header. This is caller-selected attribution, **not verified identity or authorization**. Portal selection is UI navigation, not an identity check. This is not suitable for internet exposure.

## Provider-linked service schedules

| Method      | Path                                      | Request / behavior                                                                                      |
| ----------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| POST        | `/api/service-schedules`                  | `{household_id, asset_id, provider_id?, case_id?, next_service_on, note?}`; 201, one schedule per asset |
| GET / PATCH | `/api/service-schedules/{id}`             | Read; update `{expected_revision, next_service_on?, status?, note?}`                                    |
| GET         | `/api/households/{id}/service-schedules`  | Household schedules                                                                                     |
| GET         | `/api/providers/{id}/service-schedules`   | Provider/company schedules                                                                              |
| GET         | `/api/households/{id}/service-reminders`  | Household audience reminders                                                                            |
| GET         | `/api/providers/{id}/service-reminders`   | Provider audience reminders                                                                             |
| POST        | `/api/service-reminders/check`            | `{as_of?}`; bounded check, default UTC today; no external effects                                       |
| POST        | `/api/service-reminders/{id}/acknowledge` | Matching audience attribution; acknowledgment only                                                      |
| GET / POST  | `/api/service-schedules/{id}/contacts`    | Read contacts; provider creates `{expected_revision, kind: "local_message" or "contact_note", content}` |

Mutations require `X-Demo-Role: household|provider`; provider writes can explicitly identify the selected local directory record via `X-Provider-ID`. This is caller-selected attribution, not identity security. Provider ID may otherwise be inferred from an unambiguous relevant assignment. A linked case must match the asset/household/assigned provider and not be cancelled. Dates are `YYYY-MM-DD`; status is active/cancelled. Stale revisions return 409. Identity/link fields are immutable. Schedule/reminder/contact lists support `limit` (default 100, max 200) and `offset`; schedules optionally filter status and reminders accept `include_history=true`.

Background checks run at startup/every 60 seconds by default, creating separate upcoming (within seven days) and due reminders for both audiences. Unique schedule/revision/stage/audience keys prevent duplicates on repeated checks/restart/concurrent checks. Rescheduling/cancellation supersedes old reminders. Note-only updates preserve the reminder cycle. Contacts save locally and acknowledge current provider reminders, without claiming outbound delivery. Reminder/contact responses include `external_effect: false`; reminder channel is `in_app`. Asset next-service date is mirrored when safe without overwriting independently edited dates. Cancelled schedules/retired assets do not create reminders. The worker runs only while the backend runs; startup catches missed dates.

## Local coordination endpoints

| Method | Path                                                  | Role / body                                                                                     |
| ------ | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| PATCH  | `/api/households/{id}/location`                       | household; `{address, latitude, longitude}`                                                     |
| PATCH  | `/api/providers/{id}/location`                        | provider; `{address, latitude, longitude}` (address saved as `shop_address`)                    |
| GET    | `/api/cases/{id}/nearby-providers`                    | saved-coordinate, category-matching available shops, sorted by straight-line Haversine distance |
| GET    | `/api/cases/{id}/coordination`                        | persisted state; 404 before start                                                               |
| POST   | `/api/cases/{id}/coordination/start`                  | household; `{expected_revision}`                                                                |
| POST   | `/api/cases/{id}/coordination/consent`                | household; `{offer_id, approve_cost, approve_timing}`                                           |
| POST   | `/api/cases/{id}/coordination/mock-provider-response` | provider; `{offer_id, response: "accept" \| "decline" \| "complete"}`                           |

Location coordinates must be supplied together or both omitted/null; an address is not geocoded. Creation also accepts optional location fields (`address` for household, `shop_address` for provider). Unknown-distance shops are excluded; missing household coordinates return 409.

Coordinator responses include `{case_id, mode: "local_mock", real_calls_supported: false, state}`. State holds the immutable offer ID/revision/provider, fixture total, timing, coordinate-distance selection, cost/timing consent, provider response, and truth-labeled persisted mock messages. Status progresses through `awaiting_household_consent`, `assigned`, and `provider_reported_completion`. Start uses INR 1,500 and next-day 10:00–12:00 UTC fixtures; never describe these as a live quote or appointment. Both consents must be submitted together before mock assignment. Existing payment actions cannot bypass timing consent. Stale revisions/offers are rejected; repeated assignment/completion has no duplicate effect. Completion creates simulated evidence and notification, never household confirmation. Caller-selected role is not real provider identity.

## Asset fields and category

`POST /api/assets` requires `household_id`, `name`, `category`, `location`, and `installed_on` (date). `brand` and `model` default to empty strings; `notes` defaults to an empty string. `purchased_on`, `warranty_until`, `next_service_on`, and `serial_number` may be omitted (`null`); optional dates are not manufacturer-verified. Categories are `water_purifier`, `air_conditioner`, `refrigerator`, `washing_machine`, `dishwasher`, `microwave`, `geyser`, `fan`, `electrical`, `plumbing`, `carpentry`, `pest_control`, `furniture`, `lift`, `general`, `other`. A new case derives its `service_category` from its asset; provider trade matching uses that category, not a free-text chat guess. `PATCH /api/assets/{asset_id}` updates inventory fields/status; it does not change the asset's category.

## Service chat (local rules, not live inference)

The chat request/response schema lives in `backend/app/schemas/chat.py`. All seven chat/queue routes above require the matching `X-Demo-Role`; omitting it or selecting the other role returns 403. This header and supplied IDs are not authentication or household/provider identity verification.

- Start with `POST /api/chat/conversations` body `{"household_id":"household-sangamesh"}`; the detail response includes an initial `assistant` message. List requires the `household_id` query parameter. Each summary contains `id`, `household_id`, nullable `case_id`, nullable `asset_id`, nullable `draft_complaint`, `stage`, `status`, `created_at`, `updated_at`; detail adds `messages` (`id`, `conversation_id`, `role`, `content`, `truth_label`, `created_at`). Roles are `customer`, `provider`, `assistant`.
- `POST /api/chat/conversations/{conversation_id}/messages` accepts `{"text":"The purifier is not working"}`; `text` is required (1–2000 characters), `asset_id` is optional (null by default), and `action` defaults to `message` with allowed values `message`, `confirm_report`, `cancel_report`. Supply an active asset ID belonging to the conversation's household to select it. The assistant may move from `ready` to `await_asset`, then `await_problem`, then `confirm_report`; selecting the asset directly moves to `await_problem`. A problem description of at least ten characters becomes a draft. Free-text “yes” does **not** create a case. Only explicit `action: "confirm_report"` from a valid draft creates a case in `awaiting_quote`, with no quote/provider/booking/charge. `cancel_report` discards the draft, not an existing case; invalid confirmation returns 409.
- The assistant also reads locally stored case status, appliance inventory and recorded service dates, and gives a non-dispatch emergency warning for matched urgent wording. These are deterministic rules/database lookups, not live AI, diagnosis, warranty verification or emergency assistance. Messages and drafts are stored locally; a reset of RK-2048 does not erase unrelated chat history.
- The queue includes cases assigned to `provider_id` and unclaimed cases in `awaiting_quote` whose `service_category` matches that provider's trade. The conversation-list route returns 403 unless that ID is the _currently assigned_ provider of the case. `POST /api/chat/conversations/{conversation_id}/provider-messages` takes `{"provider_id":"provider-record-id","text":"Local update"}`; the provider must be the current assigned provider on the linked case, and replies are denied for closed/cancelled cases. These checks scope the workflow; they do **not** verify who supplied the provider ID. No real provider is contacted or replies through an external service.
- Local customer/provider messages carry `REAL_HUMAN_INPUT` provenance; assistant replies carry `DOCUMENTATION_SIMULATION`. Neither label verifies identity, physical work or correctness; no `LIVE_API` chat inference/response is implemented.

## Request examples

```json
{ "asset_id": "asset-kent-purifier", "complaint": "Low water flow" }
```

Unlike the fixed RK-2048 documentary case, a new case starts in `awaiting_quote`, with `quote_amount: null`, `provider_id: null` and no spend approval. After recording an asset and matching provider, submit the quote:

```json
{
  "provider_id": "provider-record-id",
  "amount": 1200,
  "service_description": "Replace thermostat and verify cooling",
  "expected_revision": 1
}
```

Service revisions increase whenever a quote changes; stale amounts/providers cannot reuse approvals. After approval and mock assignment, the assigned provider may report actual _claimed_ work:

```json
{
  "provider_id": "provider-record-id",
  "expected_revision": 2,
  "work_performed": "Replaced the thermostat",
  "observed_result": "Checked cooling after repair"
}
```

This stores `REAL_HUMAN_INPUT` evidence, not independent verification or a completed case. The household can instead end an unassigned case with `POST /cases/{id}/cancel` body `{"reason":"No service required"}`. Retiring an appliance is blocked until its cases are closed/cancelled. See [working model guide](working-model.md).

Approval resolution does not accept an arbitrary amount or target:

```json
{ "kind": "spend", "decision": "approved" }
```

Other approval kinds are `change_provider` and `share_sensitive`; decisions are `approved` or `rejected`. Request the non-spend scope first:

```json
{
  "kind": "change_provider",
  "reason": "Request a different demo provider",
  "target_provider_id": "provider-aqua-care"
}
```

```json
{
  "kind": "share_sensitive",
  "reason": "Request the fixed minimum in-app coordination payload"
}
```

Run actions separately; requests cannot override their approved scope:

```json
{ "action": "payment" }
```

Other actions: `change_provider`, `share_sensitive`. Missing approval returns 403; stale/invalid workflow can return 409. Matching repeated payment returns the prior result without a second mock charge.

Both confirmation endpoints accept:

```json
{ "confirmed": true, "note": "I checked the documented result." }
```

`false` clears that party's flag and reopens the case. Even positive confirmation is rejected without current approved service, assignment and evidence. Two-party closure uses the same guard in manual and scripted modes.

Generic events accept only `customer_note` or `emergency` plus `detail`. They cannot forge evidence, authorization or closure.

```json
{ "name": "Demo household", "email": "demo@example.test", "consent": true }
```

Signup performs no delivery. A duplicate normalized email returns 409. No public endpoint lists signup emails.

## Errors and validation

- 200: query or accepted mutation; 201: case/signup created.
- 403: scoped permission or supplied demo attribution denied.
- 404: missing resource.
- 409: incompatible workflow, duplicate signup or stored-state conflict.
- 422: invalid shape/type/enum/limits; extra fields rejected. Validation output omits submitted raw input.
- 503: database unavailable or mock connector transition failed and rolled back.

Domain error: `{"detail":"Human-readable safe reason"}`. Validation: `{"detail":[{"type":"...","loc":["body","field"],"msg":"..."}]}`. Important denials persist a safe decision after rolling back partial transitions. Timestamps and truth labels belong to records, not inferred by the browser.

No pagination, public auth or arbitrary evidence-upload endpoint is claimed. These are explicit future deployment requirements, not hidden placeholder buttons.
