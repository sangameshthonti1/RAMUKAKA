# Use the full local working model

This guide covers **new cases**, independently of RK-2048's scripted demonstration. Records are committed to `backend/data/ramukaka.db` by default and persist after stopping/restarting. The root (`/`) is a portal chooser, not an authenticated login. Household tasks live under `/customer`; provider tasks under `/provider`; the scripted demo and documentary pages under `/project`. Migrations upgrade the schema without resetting existing records.

## Start and inspect the database

From the project root, run `bash scripts/dev.sh` and leave the terminal open. Visit http://127.0.0.1:5173 for the portal choice and http://127.0.0.1:8000/docs for Swagger. The backend migrates to Alembic head (`0005_service_schedules`) automatically and seeds RK-2048 only if missing. `0003` adds nullable purchase, warranty-expiry and next-service dates plus serial number to assets, and tables for persisted chat conversations/messages; it does not reset existing cases. Existing non-demo cases, providers, household records, conversations and signups survive simulation reset and restart. There is no browser-only fake-data fallback if the backend goes down.

Before applying `0003` to an older database, or before risky experiments, run `backend/.venv/bin/python scripts/backup_db.py` from the root. The SQLite backup API safely snapshots a running database; backups go to ignored `backend/data/backups/`, have unique UTC names, and pass SQLite `PRAGMA integrity_check`. Before the earlier `0002` upgrade, the existing database was backed up and original columns/rows compared by SHA-256 afterward. For a manual restore, **stop both servers first**, keep the current database in a separate file, and replace the database with the chosen verified snapshot; do not run a migration downgrade to restore user data. A snapshot from an older schema is upgraded to head on restart. Set `DATABASE_URL` if you explicitly chose a different local file; the backup tool honors it.

## Register the next service and remind both parties

1. **Customer:** open My Home (`/customer/home`), select **Household for service schedules**, expand **Create a service schedule**, then select the asset, matching provider, next service date and optional note/assigned case. Save.
2. **Provider/company:** select its record in Provider Desk (`/provider`) and use the same Service schedules form. It can register an eligible asset's date or revise an existing linked schedule under its local provider attribution.
3. The backend checks schedules at startup and every 60 seconds. Within seven days before the date it creates an upcoming reminder for each side; on/after the date it creates due reminders. Both portals show their own reminders and refresh every 15 seconds. Keep the backend running; missed dates are processed after restart. **Check due reminders now** can run an immediate local check without waiting.
4. The provider sees a reminder asking it to contact the customer. In **Message or contact note**, save a follow-up question or note. It appears in the customer's schedule contact history and acknowledges the provider's current reminder. This is saved portal communication, not proof of an actual call or SMS. The customer can separately acknowledge their reminder.
5. Use **Reschedule or update note**, **Cancel schedule**, or **Reactivate schedule** as needed. Date/status changes create a new revision and retire obsolete reminders; note-only updates do not generate duplicate reminder cycles. Retired assets/cancelled schedules do not produce reminders.

Each asset has one provider-linked schedule. Simply editing its standalone `next_service_on` field does not enable reminders without this schedule. Scheduled dates are plans, not confirmed bookings; no payment or external contact is implied. The normal database was backed up and upgraded to `0005_service_schedules`, with all pre-existing values preserved and integrity `ok`.

## Automatic local coordination

1. In `/provider`, select or create a provider matching the appliance category. Expand **Shop location for nearby matching**, enter its recorded address and latitude/longitude, and save. Use demo coordinates only; the directory is not verified.
2. Create a repair case in customer chat or My Home and open `/customer/cases/<caseId>`. Save household latitude/longitude in **Local automatic coordination**. An address alone is not geocoded. This is one-time location setup, not a live search.
3. When an eligible unassigned case has no selected provider and matching shop coordinates exist, the open customer case page automatically prepares the offer. It selects the nearest available recorded matching provider by Haversine straight-line distance. Missing-coordinate providers are excluded. No real call occurs; the provider acceptance and stored transcript are explicitly simulated.
4. Review the **INR 1,500 all-inclusive fixture total** and **next-day 10:00–12:00 UTC fixture slot**. Check both cost and timing consents, then submit once. Separate partial decisions cannot accumulate into authorization. Assignment is automatically recorded with a mock receipt; no real charge or booking happens.
5. In the selected provider's case view, click **Report simulated completion (mock)**. The coordinator stores simulated evidence, provider confirmation and a local customer notification. Customer dashboard notifications refresh every five seconds; the coordination state refreshes every three seconds while its page is open.
6. The customer sees **provider-reported completion**, not verified successful repair. Household verification remains independent; unresolved service can still be reported. Reload/restart preserves the transcript and offer.

`0004_local_coordination` adds nullable household/shop locations and persisted coordinator state. It does not invent locations or populate shops for existing records. The existing database was backed up before upgrade; all prior table values were compared afterward and remained unchanged, with SQLite integrity `ok`. This is UI-triggered local fixture automation, not an unattended external-calling background service. If coordinates/providers are unavailable, the manual path below remains usable.

## End-to-end new case (manual alternative)

1. At `/`, choose **Open customer portal**. In `/customer/home` (**My Home**), create a household with a member or use an existing one. Add an appliance in one of 16 categories, including appliances, electrical, plumbing, carpentry and pest control. Record name, location and installation date; optionally record purchase date, warranty expiry, next service date and serial number. These are **household-entered, unverified** dates, not manufacturer-confirmed warranty or a booked visit. Editing inventory persists; retiring an asset preserves its case history (retirement is blocked while a case is open).
2. At `/customer/chat`, choose a household and start a conversation. Ask about the recorded appliances, service dates/history or case status; the assistant replies from stored local records using deterministic rules, not a live AI model. To request a repair, choose an active appliance, describe the problem (at least ten characters), review the saved draft and click **Confirm repair request**. Free-text alone never creates a case; **Cancel draft** discards it. Alternatively use **Report an issue** in My Home. The new case is `awaiting_quote` with **no provider, plan or amount**; no ₹749 fixture is applied to new cases. The conversation and draft survive reload/restart.
3. Choose **Open provider portal** at `/` (or visit `/provider`). Add an **unverified local provider record** with a matching trade, or select an available existing record from the directory. Open its queue and case, for example via `/provider?provider=<id>&case=<caseId>`. Only unassigned matching-trade requests and cases assigned to the selected record appear in that queue. Enter the proposed service and whole-INR quote. The backend records locally attributed human input, creates a scoped pending approval and logs the service-plan revision. Selection and header attribution do **not** verify the submitter's identity.
4. Return to `/customer/cases/<caseId>`. Review and approve or reject the quote, then click **Assign approved provider (mock)** once approved. A server-side guard refuses the mock payment/assignment without approval; repeats cannot create a second mock receipt. No actual charge, appointment or provider booking occurs.
5. In the selected provider's case view, an **assigned** provider can post a local message to the linked conversation, submit a report of work performed and observed result, and confirm completion. Messages persist and appear in the customer's chat; they are not delivered externally or independent service evidence. The report is `REAL_HUMAN_INPUT`—an _unverified local claim_, not a certified visit or live API response. The backend requires the current approved assignment and provider/revision; a new report clears older confirmations.
6. Provider confirmation alone leaves the case open. The household independently records confirmation in `/customer/cases/<caseId>`. The case closes only after current service evidence and **both** confirmations exist. Either party reporting unresolved reopens it; follow-up work requires a new report and confirmations.
7. Reopen the browser or restart the backend: appliance dates, conversation/messages, linked case, timeline, audit, evidence, provider and status remain in SQLite. Use `/project/evidence` to inspect reason/rule and truth label for each record. `/project/simulation` can reset `RK-2048` independently without deleting this new case.

A household can request a different provider through the scoped approval in the case view. For a new case, applying the approved switch discards the prior provider's price and plan; the replacement provider must submit a fresh quote for household approval. No old approval may fund the new assignment.

If a household no longer needs service before assignment, cancel the unassigned case from `/customer/cases/<caseId>` with a reason. Cancellation revokes outstanding permissions, preserves history, and does not count as completed work. Assigned work cannot be erased by cancellation; resolve it through the service process.

## Honest limitations

This is a **local data-backed demonstration**, not an internet-safe production deployment. Portal choice and `X-Demo-Role` are caller-selected attribution, **not authentication**. Any local user could impersonate another role or inspect records; no tenant isolation is implemented. Do not store real personal/financial information, and never expose the backend publicly. Chat replies are deterministic, not live AI; warranty dates and AMC coverage are not checked with manufacturers. Provider entries are not vetted, evidence is not cryptographically verified, and mock integrations never move money, deliver external messages or make bookings. Real service requires authenticated accounts and permissions, secure attachments, verified providers, trusted rails and operational controls before deployment.
